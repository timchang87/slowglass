A studio that shows, so you can act

A desktop tool for relearning the whole production chain (arrangement, sound design, mixing, mastering) in Ableton Live 12 Lite, starting with house. It finds reference material, analyses it, mirrors your own set back to you, versions your ideas, and teaches through hints rather than answers.

The tool shows (analysis, visuals, discovery) You act (knobs, downloads, decisions) Off limits

Settled decisions

Everything below came out of the grilling session and is fixed until you change it.

Goal
Music first. The tool is a real build too. House/electronic, foundations before artistry.
Time
10 h/week: 6 music, 4 build. Using the tool is your UAT. Music starts in week 1 without the tool.
Rig
Mac mini M4 24 GB · Live 12 Lite (8 tracks, 2 returns) · Sylenth1 + stock · MOTU M2 loopback · near-fields in a bare room.
App
Electron shell + Python sidecar. The sidecar is also an MCP server: Claude Code now, in-app agent later.
Live access
Read-only, behind a LiveBridge seam. Week 1 decides AbletonOSC (vendored) or our own Remote Script.
Sources
Crawl for discovery only where allowed. You always download. Each site has a mode in the source registry.
Versioning
Auto snapshot on save, named snapshots ask for a bounce, branches without merge. Git stores lossless XML through a filter; you read a YAML summary diff. Project and branch live in a thin status footer on every view. Each song gets a private GitHub remote for off-site history.
Data
SQLite for facts, files for things, git per song, audio as plain files. Open-source-ready: links and analysis only.
Teaching
Two loops (study a reference, then your song). Skill tree with evidence. Lessons generated on reach. Ear-drill warm-up. Hint ladder behind problem / tried / hypothesis.
Coach runtime
Rules in Python, words from Claude. Phase 1: /stuck and /lesson in Claude Code over MCP. Phase 2: the same tools in an in-app agent.
Browser
No built-in browser. Links open in your default browser; a Downloads watcher and a bookmarklet bring files and pages back.

Design principles

  • Shows, never playsThe tool never turns a knob, writes a clip, or renders a mix. It draws what is happening and asks questions. Struggle is part of the product.
  • Hint, not answerNo hint until you state the problem, what you tried, and what you think it is. The ladder starts at "where" and only reaches "the exact move" on request, and every rung-5 hint is logged against the skill.
  • You click DownloadCrawlers read listing pages to build the catalogue. Every file download is a human action in a browser. The tool takes over after the file lands.
  • Facts in the DB, things in filesSQLite can always be rebuilt from the files plus a re-run of analysis. Nothing irreplaceable lives only in the database.
  • Seams over betsLiveBridge, source adapters and the MCP surface are interfaces, so AbletonOSC, a crawl mode or the agent runtime can be swapped without touching the rest.
  • Evidence over claimsA skill moves up only on evidence: a passed drill, a diff showing the technique applied, a completed study.

Architecture

Everything runs on the Mac mini. The Python sidecar holds all the logic. Electron is the visual surface and Claude reaches the same capabilities through MCP.

Versioning format

Two layers, because restoring and reading need different things. Live only opens .als, which is gzipped XML, so the restorable copy must be exactly what Live wrote.

LayerFormatWhereJob
Working file.als (gzip XML)Song folderWhat Live opens and saves. Never touched by the tool.
Stored historyPlain XMLSong git repo, via a clean/smudge filterLossless restore and branching. Git stores small edits as small deltas, which it cannot do with gzip.
Readable summaryYAML, a few KB.slowglass/summary.yaml per versionDiffs and the Versions view. Drops view state, scroll positions and internal IDs that change on every save.
 
# .gitattributes in each song repo
*.als  filter=als diff=als

# .git/config (set up by slowglass)
[filter "als"]
    clean  = gzip -dc          # .als → XML when committing
    smudge = gzip -c           # XML → .als on checkout
    required = true
[diff "als"]
    textconv = slowglass summarize --stdin   # git diff shows the YAML summary

Samples stay out of git (Collect All and Save keeps them in the song folder; your backup covers them). Backup/ is ignored.

Crawler conduct

  • One honest user-agent with a contact URL. No browser spoofing, ever.
  • Obey robots.txt for our agent and for named AI-agent groups (ClaudeBot, GPTBot, anthropic-ai). If those are blocked, the source drops to capture.
  • Listing and detail pages only. No file downloads, no login, no paywalled pages.
  • At least 5 s between requests per host, conditional GETs (ETag), local cache, and a weekly schedule.
  • Store link, metadata and our own gist. Never rehost descriptions in full or any media.
  • Re-check each source's terms every 90 days; the registry records when.

Skill model

Each skill node moves through four states, and only evidence moves it. The tree itself (roughly 40 to 60 nodes across six stages) is a researched build task with primary sources, reviewed by you before the coach is wired to it.

Unseenno contact yet
Introducedlesson opened or study task done
Practisedapplied in a version, or drills ≥ 60%

Stages: listening (frequency ID, compression, width) · arrangement (sections, builds, transitions, energy) · sound design (subtractive synthesis in Sylenth1, drum layering, sampling) · production (groove, swing, automation, recording guitar) · mixing (gain staging, EQ, compression, sidechain, space, low end) · mastering (loudness, limiting, translation checks). Thresholds above are starting values to tune during UAT.
